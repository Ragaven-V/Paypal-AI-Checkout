# Retire thinkingBudget before Gemini 3 rejects it

Gemini 3.x models return `400 INVALID_ARGUMENT` for `thinkingConfig: { thinkingBudget: 0 }` because the integer budget is a Gemini 2.5 control. Google lists `thinking_budget` as deprecated for Gemini 3 and later, the 3.5 Flash guide says it is **"no longer supported across all Gemini 3 models"**, and Gemini 3 has no documented "off" state that a budget of 0 could map to ([Vertex AI: Thinking](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thinking); [Vertex: Gemini 3.5 Flash guide](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/guides/gemini-3-5-flash)). The `@google/genai` 2.x SDK does not catch this on the client. Its `ThinkingConfig` type still exposes `thinkingBudget?: number` with the comment "0 is DISABLED", so the bad field goes to the server, which answers with a generic error that does not name the field ([js-genai types.ts](https://github.com/googleapis/js-genai/blob/main/src/types.ts)). The fix is to remove `thinkingBudget` from every Gemini 3 request and use the discrete `thinkingLevel` instead. For a tool-calling shopping assistant that means `LOW`, not the lower `MINIMAL`, which Google warns can end tool chains early. Two other API contracts can produce 400s that look the same and are worth hardening at the same time. Explicit caching cannot be combined with per-request `systemInstruction` or `tools`, and multi-turn function-calling history must keep thought signatures and call-response pairs intact. This matters beyond this app: on **December 1, 2026**, `gemini-2.5-flash` requests start routing to `gemini-3.5-flash-lite`, so any legacy code that still sends `thinkingBudget: 0` could hit the same 400 after the cutover ([AI Studio: Models](https://aistudio.google.com/docs/models)).

## A deprecated 2.5 knob fails on every Gemini 3 model

On Gemini 2.5, `thinkingBudget: 0` turned thinking off for Flash and Flash-Lite, though not for 2.5 Pro, which already returned a 400 "does not support setting thinking_budget to 0" ([Vertex AI: Thinking](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thinking); [Google AI forum](https://discuss.ai.google.dev/t/gemini-2-5-flash-problems-while-trying-to-deactivate-thinking/96648)). Gemini 3 replaced the token budget with `thinking_level`, and Google now tells developers to **"Replace `thinking_budget` with `thinking_level`"** and to remove the budget entirely on Gemini 3 and later. Sending both parameters in one request **always returns a 400** ([Vertex: Gemini 3.5 Flash guide](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/guides/gemini-3-5-flash); [AI Studio: What's new in Gemini 3.6](https://aistudio.google.com/docs/whats-new-gemini-3.6)). Google's own pages disagree on how strictly this is enforced. The general thinking page says the budget "can cause intermittent errors" on Gemini 3 and fails outright on Gemini 4, while the 3.5 Flash guide calls it unsupported on all Gemini 3 models ([Vertex AI: Thinking](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thinking)). This project saw a consistent 400 on `gemini-3.5-flash-lite`, which fits the stricter wording. No official page says in so many words that a budget of 0 in particular is rejected. The model ID was not the cause: `gemini-3.5-flash-lite` is a real, stable model, described as "the fastest, lowest-cost model in the 3.5 family" ([AI Studio: What's new in Gemini 3.6](https://aistudio.google.com/docs/whats-new-gemini-3.6)).

Thinking cannot be fully turned off on Gemini 3. No official source documents a way to do it. The floor is `MINIMAL`, and not every model accepts it ([AI Studio: Thinking](https://aistudio.google.com/docs/thinking)). In SDK 2.x the correct field is `config.thinkingConfig.thinkingLevel`, whose `ThinkingLevel` enum values are the uppercase strings `"MINIMAL"`, `"LOW"`, `"MEDIUM"` and `"HIGH"`. The Interactions API instead uses a snake_case `generation_config.thinking_level` with lowercase values, which explains why some current AI Studio samples look different ([js-genai types.ts](https://github.com/googleapis/js-genai/blob/main/src/types.ts); [AI Studio: Thinking](https://aistudio.google.com/docs/thinking)).

| Model | Accepted thinking levels | Default |
|---|---|---|
| Gemini 3.5 Flash-Lite, 3.1 Flash-Lite | MINIMAL, LOW, MEDIUM, HIGH | MINIMAL |
| Gemini 3.5 Flash, 3.6 Flash | MINIMAL, LOW, MEDIUM, HIGH | MEDIUM |
| Gemini 3 Flash (preview) | MINIMAL, LOW, MEDIUM, HIGH | HIGH |
| Gemini 3.7 Flash, 3.8 Flash | LOW, MEDIUM, HIGH | MEDIUM |
| Gemini 3.1 Pro (preview) | LOW, MEDIUM, HIGH | HIGH |
| Gemini 4 Argon | LOW, MEDIUM, HIGH | MEDIUM |
| Gemini 2.5 family | `thinkingBudget` only; do not send `thinkingLevel` | model-dependent |

Source: [Vertex AI: Thinking](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thinking). Pro models and the newest Flash models do not accept `MINIMAL`, so code that hard-codes `MINIMAL` will fail when the model is upgraded. A level that works on every current Gemini 3+ model is `LOW`, which is another reason to use it as the default.

## LOW thinking with no sampling overrides fits a tool-calling assistant

A shopping assistant should send `thinkingLevel: "LOW"` even though `MINIMAL` is the fastest setting. The 3.5 Flash-Lite model card warns that **"using the minimal thinking level can cause premature tool termination on multi-step tasks"**. It recommends `MINIMAL` for classification and extraction, `LOW` for high-throughput work that needs light reasoning, and `MEDIUM` or `HIGH` for agents that call external APIs ([Vertex: Gemini 3.5 Flash-Lite](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash-lite)). Search, add-to-cart and checkout flows that chain several tool calls sit between those cases. `LOW` is a reasonable default, with `MEDIUM` as the next step up if the model stops tool chains too early. To cut latency, Google advises lowering the thinking level rather than setting a small `maxOutputTokens`, which cuts the response off at a hard limit ([AI Studio: Thinking](https://aistudio.google.com/docs/thinking)). No published benchmark compares the latency of `MINIMAL` and `LOW` on 3.5 Flash-Lite, so the actual cost of `LOW` has to be measured in this app.

Sampling parameters should be removed. Gemini 3.5 Flash-Lite ignores custom `temperature`, `topP` and `topK`, and custom frequency or presence penalties **already throw an error** ([Vertex: Gemini 3.5 Flash-Lite](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash-lite)). The 3.6 guide says supplying temperature, top-P or top-K will return HTTP 400 "in future model generations", and that they should be removed from all requests now ([AI Studio: What's new in Gemini 3.6](https://aistudio.google.com/docs/whats-new-gemini-3.6)). When you need deterministic behaviour, Google's answer is explicit rules in the system instruction rather than a low temperature ([Vertex: Gemini 3.5 Flash guide](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/guides/gemini-3-5-flash)). Two rules on request structure complete the config. A request whose final `contents` entry has role `model` returns an error. Every `FunctionResponse` must echo the `id` of its `FunctionCall`, with exactly one response per call, and mismatches typically produce empty replies with `finish_reason: STOP` instead of a clear error ([Vertex: Gemini 3.5 Flash-Lite](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-5-flash-lite); [Vertex: Gemini 3.5 Flash guide](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/guides/gemini-3-5-flash)).

## Explicit caching rejects per-request tools and rarely pays at small sizes

A `generateContent` or chat request that sets `cachedContent` **cannot also set `systemInstruction`, `tools` or `toolConfig`**. The API returns 400 INVALID_ARGUMENT: "CachedContent can not be used with GenerateContent request setting system_instruction, tools or tool_config", and the server's own suggested fix is to move those values into the cache ([Google AI forum](https://discuss.ai.google.dev/t/structured-output-support-with-cached-content/41525); [Vertex AI: Use a context cache](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-use)). Those values have to be set in `caches.create`. A per-request `toolConfig` overrides the cached one and can cut off function calling, so apps that vary `allowedFunctionNames` need one cache per set of functions ([Google AI forum](https://discuss.ai.google.dev/t/different-configtool-on-every-api-request/107329)). `responseSchema` and `responseMimeType` cannot be cached and stay on the request ([Google AI forum](https://discuss.ai.google.dev/t/support-caching-response-schema-structured-output-config-in-createcachedcontentconfig/183271)). The error names only those three fields, which suggests `thinkingConfig` is still allowed on the request, but no doc lists every allowed field. The cache's `contents` also needs at least one user-role entry ([Google Cloud community](https://discuss.google.dev/t/vertex-ai-caching-only-system-prompt/170079)).

Size limits make explicit caching impractical for a small catalog. The current Gemini API docs set a **4,096-token minimum** for Gemini 3.x models (3.1 Pro Preview, 3.6 Flash, 3.8 Flash) and for Gemini 4, against 2,048 for 2.5 models ([Gemini API caching docs](https://aistudio.google.com/docs/caching?generate-content=true)). Vertex also gives 4,096 for most Gemini 3 models, with a 6,144-token threshold for some models that applies to implicit caching only ([Vertex AI context caching overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)). No doc lists the minimum for 3.x Flash-Lite. The minimums the server enforces have drifted from the documented ones before, so trust the `min_total_token_count` value in the "Cached content is too small" 400, or call `countTokens`, rather than hard-coding a number ([Google AI forum](https://discuss.ai.google.dev/t/context-caching-docs-list-wrong-minimum-token-count-for-gemini-2-5-flash-flash-lite-missing-entirely/178942)). Explicit caching is also not supported on Gemini 4 Argon or later, or in the Interactions API ([Gemini API caching docs](https://aistudio.google.com/docs/caching)). Implicit prefix caching is on by default for Gemini 2.5 and newer, with no storage fee, but discounts are not guaranteed. A request that uses an explicit cache does not get implicit-cache discounts on top ([Gemini API caching docs](https://aistudio.google.com/docs/caching)). If a cache stays under the minimum, the simplest correct design is to send `systemInstruction` and `tools` on every request and keep them as a stable prefix so implicit caching can apply once the catalog grows.

Caches expire. **The default TTL is 1 hour** and there is no maximum, though Vertex sets a 1-minute minimum. `caches.update` can change only `ttl` or `expireTime`, and storage is billed per token-hour for the whole TTL ([Gemini API caching docs](https://aistudio.google.com/docs/caching?generate-content=true); [Vertex AI context caching overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview)). Once a cache expires it is marked for deletion and should not be reused ([Vertex AI: Use a context cache](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-use)). Client libraries treat later 403 or 404 responses as "cache expired" ([rig-core](https://docs.rs/rig-core/0.44.0/src/rig_core/client/cached_content.rs.html)). The robust pattern is to catch that error, recreate the cache and rebuild the chat. A cache is also tied to the model it was created with, so it should be recreated whenever the configured model ID changes ([Vertex AI: Use a context cache](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-use); [gemini-review-action v1.3.5](https://github.com/derailed-dash/gemini-review-action/releases/tag/v1.3.5)).

## Function-calling history breaks at signatures, ordering and trim points

Gemini 3 requires thought signatures to be passed back during function calling, **even at `MINIMAL` thinking**. A missing signature returns 400 "Function call `<name>` in the `<n>` content block is missing a `thought_signature`" ([Thought signatures](https://aistudio.google.com/docs/thought-signatures?generate-content=true); [Vertex: Thought signatures](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thought-signatures)). Strict validation applies only to the "current turn". That turn begins at the most recent user message with ordinary content such as text, not at a `functionResponse`. Within it, the first `functionCall` part of every model step must keep its signature ([Thought signatures](https://aistudio.google.com/docs/thought-signatures?generate-content=true)). The JS chat object keeps signatures automatically because it stores each response's raw `Content`, including when streaming. `getHistory()` returns a `structuredClone`, so slicing it keeps every field ([js-genai chats.ts](https://github.com/googleapis/js-genai/blob/main/src/chats.ts)). Signatures are lost when code rebuilds model turns from `response.functionCalls`, which returns bare `{name, args, id}` objects without the enclosing Part, or merges signed and unsigned parts ([Function calling](https://aistudio.google.com/docs/function-calling?generate-content=true)). Dummy values such as `"skip_thought_signature_validator"` exist for injected or migrated history, but Google strongly discourages injecting function calls the API did not generate ([Thought signatures](https://aistudio.google.com/docs/thought-signatures?generate-content=true)).

Turn order follows a strict pairing. A model turn with `functionCall` parts must be followed directly by **one user turn holding all the matching `functionResponse` parts**. Parallel calls go as FC1 (signed), FC2, then FR1, FR2. Interleaving them as FC1, FR1, FC2, FR2 returns a 400 ([Thought signatures](https://aistudio.google.com/docs/thought-signatures?generate-content=true)). Older error text makes the contract explicit: the response turn must come "immediately after a function call turn", with equal numbers of call and response parts ([firebase-ios-sdk #14022](https://github.com/firebase/firebase-ios-sdk/issues/14022)). Only the first parallel call carries a signature. js-genai issue #1275, first reported as the model signing calls inconsistently, was retracted once the reporter found their own code had split parallel calls into separate model messages ([js-genai #1275](https://github.com/googleapis/js-genai/issues/1275)). Match responses to calls by `id`, because the docs contradict themselves on whether order matters ([Function calling](https://aistudio.google.com/docs/function-calling?generate-content=true)). One risk remains unresolved. The SDK's streaming path stores each chunk as a separate `model` Content. If Gemini 3 ever spreads parallel calls across chunks, that would recreate the #1275 shape without any user error. Neither the chunking behaviour nor whether the backend tolerates it is documented ([js-genai chats.ts](https://github.com/googleapis/js-genai/blob/main/src/chats.ts)).

Two rules make history trimming safe. Start a slice only at a user turn whose parts are text and contain no `functionResponse`, and never keep a `functionCall` turn without the response turn that follows it. The SDK will not catch a mistake here. Despite its JSDoc, `validateHistory` checks only that roles are `user` or `model`, so a history that starts with an orphan `functionResponse` goes to the API ([js-genai chats.ts](https://github.com/googleapis/js-genai/blob/main/src/chats.ts)). Failure handling has its own trap. A rejected `sendMessage` records nothing. But when a model turn is empty or invalid, `getHistory(true)` drops it **along with the user turn before it**. If that user turn was a `functionResponse`, the earlier `functionCall` is left dangling and the next message gets an ordering 400. Stream history is written only after the generator is fully drained, so breaking out of the loop early when tool calls appear leaves the turn out of history ([js-genai chats.ts](https://github.com/googleapis/js-genai/blob/main/src/chats.ts)). Discarding the chat after any failed turn avoids carrying a broken history forward. On the reading side, `chunk.text` warns whenever a chunk contains non-text parts such as `functionCall`. Iterating `candidates[0].content.parts` directly, skipping `thought` parts, avoids the warning and handles signature-only empty-text parts correctly ([js-genai types.ts](https://github.com/googleapis/js-genai/blob/main/src/types.ts)).

## How this project was affected and fixed

In this project, every chat request failed with 400 INVALID_ARGUMENT. A direct `generateContent` call to the same model succeeded without `thinkingConfig` and failed with `thinkingBudget: 0`, which isolated the cause to the deprecated field. The damage went unnoticed because the app silently fell back to a rule-based mock assistant while the UI still showed "Gemini Live AI". The fix removed `thinkingBudget`. Thinking is now set by `GEMINI_THINKING_LEVEL` (default `"low"`), which is sent as `thinkingLevel: "LOW"` to Gemini 3 models, with `thinkingBudget` used only for 2.5 models. Explicit caching is now opt-in (`GEMINI_EXPLICIT_CACHE=true`), and when it is on, `systemInstruction` and `tools` live inside the cache instead of on the request. History trimming starts only at user text turns, and a failed turn discards the chat. Streaming reads parts directly instead of `chunk.text`. A startup self-check sends the production config once at boot and logs loudly if it fails. `/api/config` now exposes `aiDegraded`, so the UI shows when the fallback is in use. A live end-to-end test (`GEMINI_LIVE_TEST=1`) passes against `gemini-3.5-flash-lite` with `thinkingLevel` LOW, and a unit test asserts that `thinkingBudget` is never sent to Gemini 3 models.

## Conclusion

The bug's real cost came from the silent fallback, more than from the 400 itself. A one-field config error turned into an outage that looked like a working product, because the failure path was well enough designed to hide that it was running. The boot-time self-check and the `aiDegraded` flag matter more than the one-line fix, because they turn the next API contract change into a visible error. The fix itself is less of a guarantee than it looks. The level-to-model table changes with each release, and newer Flash and Pro models already reject `MINIMAL`. The config should therefore branch on model family and be covered by a live test, not hard-coded once.

Four mechanisms in this stack can return 400 INVALID_ARGUMENT for different reasons: thinking config, cache-versus-tools conflicts, missing signatures and broken call ordering. They share an error code and often a generic message, so a single 400 says little about which one fired. The useful diagnostic is the one this project used: replay the exact production config against the live API with fields removed one at a time. With 2.5 Flash traffic starting to route to 3.5 Flash-Lite on December 1, 2026, other teams with older Gemini integrations should expect to run the same check.
